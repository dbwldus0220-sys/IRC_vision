최신 코드로 재실행한 기존 재현 및 경계 가설 통합 재현

제어 소스/설정을 추가로 변경하지 않았다. 실제 로봇/카메라/ROS 그래프를 실행하지 않았다.

1. 기존 로그 기반 가정 입력 재실행
compare.py의 변경 전후 결과와 assertion을 다시 확인했다.
기본 조건은 전후 모두 모션 종료 +134.257ms에 첫 공 접근 명령, 사전 예약 없음.
후보 입력을 150ms 또는 300ms 앞당긴 조건은 새 코드에서 사전 예약에 성공했다.
이전 결과와 동일하며 실제 프레임별 검출을 복원한 재생은 아니다.

2. 부분 상자 -> 전체 상자 가정을 전체 판단 흐름으로 연결
combined_replay.py에서 실제 TemporalConfirmationFilter, MotionDecisionNode,
MotionCommandBridgeNode 테스트 하네스를 연결했다.
검출 상자는 처음 3개가 [800,0,870,20], 이후 [800,0,870,80]으로 가정했다.
공 거리 .86m, 공 지면 방향 -28.57도, 유효 깊이를 고정 입력했다.
이 거리/방향은 상자로부터 추정한 결과가 아니며, 실제 영상 관측값의 시계열도 아니다.
간격은 1/10.305초, 영상 나이는 289.902ms로 두었다.
비교를 위해 기존 필터가 10회에 도달하는 13번째 입력을 종료 +134.257ms에 맞췄다.
따라서 여기의 +134ms는 이 가설이 실제 정지 원인이었다는 독립적인 증거가 아니다.

활성화 기능 / 첫 확정 / 첫 접근 명령 / 사전 예약
둘 다 없음: +134.257ms / +134.257ms / 실패
확정 전 관측 재사용만: +134.257ms / +134.257ms / 실패
경계 누적 보존만: -59.824ms / 0ms / 실패
두 기능 모두: -59.824ms / -59.824ms / 성공

모든 경우 실제 요청한 모션은 공 방향 RECOVER_LEFT_TURN_LEFT_4였다.
가정 입력에서 확정 전 명령/추가 라인 명령이 없는지 검사했다.
예약 성공 후 가짜 실행기 상태를 SUCCEEDED/RUNNING으로 넘겨 명령 ID 승계도 확인했다.
이는 실제 실행기 통신 지연/물리적인 모션 연속성을 측정한 결과가 아니다.
약 60ms 예약 여유가 실물에서도 충분한지는 아직 확인하지 않았다.

3. 보수적으로 처리하는 조건
위치까지 크게 이동한 상자로 바뀌면 전후 모두 +134.257ms이며 기존 후보 누적을 이어 쓰지 않았다.
크기 변화 직후 다음 검출이 빠지면 새 코드는 보류한 기록을 초기화한다.
이 경우 기존 +231.297ms -> 변경 후 +328.338ms로 약 97ms 더 기다렸다.
불확실한 후보를 이어 쓰지 않도록 한 처리의 비용이며, 모든 검출 상황에서 대기가 줄지는 않는다.

결론
크기 변화만으로 같은 후보를 잃는 가정에서는 두 수정의 조합이 정지 없는 예약 연결을 만들었다.
그러나 실제 녹화의 후보 초기화 사유/원본 검출이 없어 실제 테스트의 정지가 사라졌다고 확정할 수 없다.
확정 자체가 늦고 이번 경계 예외에도 해당하지 않는 경우, 또는 검출이 계속 불안정한 경우에는 대기가 남는다.

실행
source /opt/ros/humble/setup.bash
source install/local_setup.bash
python3 artifacts/20261107_ball_entry_history_replay/compare.py
python3 artifacts/20261107_ball_entry_history_replay/combined_replay.py

결과: results.json, combined_results.json (프레임별 가정 입력/확정 trace 포함).
