# 골대 라인 복귀·lost 제한 및 녹화 분석

검토 파일: `/home/sy/Downloads/Screencast from 2026년 09월 29일 02시 23분 59초.webm`.
영상 프레임과 현재 작업공간 코드를 대조했다. 영상의 실행 경로는 `IRC_vision_latest`이며,
그 장비의 실행 소스/파라미터 전체와 원본 ROS 로그는 제공되지 않았다.
아래에서 화면으로 확인한 사실과 현재 코드의 동작을 구분한다.

## 적용한 변경

- 슛 후 복귀 회전 완료가 곧바로 `LINE_TRACK`으로 넘어가던 경로를
  `POST_SHOT_LINE_ALIGN`으로 연결했다. 따라서 실제 주행 경로에서도 정렬을 확인한다.
- 슛 이후 `POST_SHOT_LINE_ALIGN`의 정렬 완료 조건을 `abs(ground_heading_error_deg) <= 20.0`으로 변경했다.
  정확히 ±20도도 완료로 인정한다. 유효한 지면 투영·라인 품질·오프셋 입력은 계속 요구한다.
  슛 후 라인이 없으면 첫 번째는 우회전 2회 모션, 두 번째는 좌회전 1회 모션으로 탐색한다.
  라인을 찾으면 각도를 보정하고 기존 완료 후 정지/새 프레임 확인 절차를 거쳐 전진한다.
  반대 방향으로 각도를 보정한 뒤 다시 라인을 놓쳐도 탐색 방향은 해당 골대 모드의 방향을 유지한다.
- 골대 복귀 복합 모션은 JSON에서 이미 우회전 9주기·좌회전 6주기를 포함한다.
  `repeat_count=1`은 준비 자세를 포함한 전체 복합 모션을 한 번 실행한다는 뜻이다.
  이를 9 또는 6으로 변경하면 전체 동작을 그만큼 반복하므로 변경하지 않았다.
  기존 액션 이름 `POST_SHOT_TURN_LEFT_4`는 호환용 이름이고 실제 연결된 좌회전은 6주기다.
- 공통 명령 발행 경로에 lost 제자리 탐색 제한을 추가했다.
  기본값은 대상별 소실 구간당 **최대 3개 회전 명령, 예상 누적 회전각 최대 90도**다.
  다음 모션이 각도 예산을 넘으면 시작 전에 막는다. 예를 들어 우측 45도 모션은 2번,
  15도 탐색 모션은 횟수 제한 때문에 3번까지 가능하다.
  우측 45도 후 좌측 30도도 총 75도로 합산한다. 실제 IMU 각도가 아닌 기존 회전 보정표 기준이다.
  골대의 필수 복귀 회전과 보이는 목표를 향한 정렬은 이 탐색 예산에 포함하지 않는다.
- 판단 후보를 반복 계산해도 예산을 사용하지 않는다. 발행한 명령만 세며 실패해도 돌려주지 않는다.
  라인/공/허들/골대별 예산은 독립적으로 보관하고, 같은 대상을 다시 검출하여 유효한
  추적 명령을 발행해야 초기화한다. 단순 검출 깜빡임·대기·센서 누락·다른 모드 진입은 초기화하지 않는다.
  한도 초과 시 `WAIT`, `valid=false`, `lost_search_turn_limit_reached`로 새 회전을 차단한다.
  보정 각도를 알 수 없는 탐색 명령은 `lost_search_turn_angle_unavailable`로 보류한다.
- 현재 공 소실 로직은 기억한 위치만으로 회전하지 않으며, 가까운 공 후진/특정 조건의 전진 복구를 사용한다.
  허들은 검출 소실 시 WAIT한다. 이 변경이 이들 모드에 새로운 맹목 회전을 추가하지는 않는다.
  골대의 기존 `RECOVER_GOAL_TURN_*`는 실행 매핑과 보정 각도가 없어 계속 실행하지 않는다.
  실행 가능한 lost 회전과 향후 보정 정보가 있는 탐색 명령 모두 공통 발행 제한을 거친다.
- 누락된 `pickup_lost_ball_backward_1` alias와 해당 모션을 복구했다.
  `catalog25_prune_backup/robot_motions_runtime.json`의 원본을 그대로 복원했으며,
  현재 `찐후진실전(1회)`와 머리 관절 0번의 -60도 및 이름 이외에는 완전히 동일함을 확인했다.
  원래 픽업 고정 묶음의 후진 2회와 구분되는 소실 복구 전용 후진 1회다.
  모든 런타임 모션의 완료 허용 오차는 5도를 유지한다.

실행 시 `full_system.launch.py`와 `full_system_robot.launch.py`에 다음 인수를 줄 수 있다.

```text
lost_search_max_turns:=3 lost_search_max_angle_deg:=90.0
```

이 설정은 실행 시작 시 읽는다. 횟수나 각도를 0으로 설정하면 lost 탐색 회전을 막는다.

## HURDLE WAIT

첨부 파일 타임스탬프 약 2:44는 LINE FORWARD 6이며, 질문과 일치하는 허들 대기는
약 3:38~3:42에서 확인된다([218초 프레임](hurdle_wait_218s.jpg)).
화면은 `HURDLE_POSITIONING / FINE_APPROACH / Detection: SEARCH`다.
직전 접근 중 허들이 화면 아래쪽으로 내려가 사라졌고, 약 3:42에는 RAW,
약 3:44에는 다시 확인된 허들에 대해 FINE FORWARD가 선택된다.

현재 허들 판단기는 `detected=false`이면 즉시 `hurdle_not_detected`로 WAIT한다.
검출은 있어도 신뢰도·거리 조건을 충족하지 못하면 다른 이유로 WAIT할 수 있다.
**좌측 정렬/허들 동작을 새로 선택하기 전 허들이 안 보이면 WAIT할 수 있다.**
그러나 GO를 받아 고정 묶음에 들어가면 미세전진 → GO 직전 대기 → 허들 모션을 진행한다.
그 안의 `HURDLE PRE GO DWELL`은 미검출 WAIT와 다르며, 이미 실행 중인 GO 묶음은
허들이 사라졌다는 이유만으로 취소하지 않는다. 실행 실패나 안전 정지는 별도다.

누락된 모션을 복원했으므로 이 거절 원인은 해결했다. 다만 공이 계속 보이지 않으면
다음 정렬 체크포인트가 기다리는 동작은 정상이며, 무조건 집기로 진행하도록 바꾸지 않았다.

화면에서 추가로 확인한 값:

| 약 3:36 ([216초](hurdle_positioning_216s.jpg)) | HURDLE_POSITIONING, FINE_APPROACH. CONFIRMED, 신뢰도 0.68, 거리 0.54m, 하단 거리 67px. |

| 약 3:44 | CONFIRMED, 거리 0.47m. 터미널에 action=GO, command_id=792가 나타남. |

현재 코드로 확인한 핵심은 근거리 진입 예약과 GO 묶음 시작이 다르다는 점이다.
`_latch_hurdle_positioning_entry()`는 움직이는 동안 55cm 이하의 유효한 허들을 보면
`hurdle_positioning_entry_pending=True`만 저장한다. 실행 중 전진을 중단하거나 GO를 예약하지 않는다.
모션 종료 뒤 `HURDLE_POSITIONING`으로 전환하고 그때의 새로운 관측으로 다시 GO 여부를 판단한다.
이때 `detected=false`이면 `HurdleNavigationPlanner.plan()`의 첫 검사에서 WAIT한다.
가까움을 기억하는 `close_rotation_blocked=True`도 이 미검출 검사를 우회하지 못한다.
깊이 소실 복구는 허들 자체가 여전히 검출될 때만 동작한다.

ROS 그래프 없는 기존 MissionFlowHarness로 다음 순서를 실제 재현했다.

```text
STRAIGHT 실행 중, 0.54m의 확정 허들 관측
  → pending=True, phase=LINE_TRACK, special_action=None
STRAIGHT 완료, 허들 미검출 입력
  → phase=HURDLE_POSITIONING, action=WAIT, reason=hurdle_not_detected
같은 근거리 허들을 새 입력으로 제공
  → action=GO, reason=hurdle_fine_sequence_at_close_depth
```

이 구조가 GO 이전 소실로 대기하는 원인을 설명한다. 재검출 초기에도 분석기는
확정 프레임 수가 부족하면 `hurdle_confirmation_pending`으로 `detected=false`를 보내므로
CANDIDATE 4/15에서 WAIT가 이어진다.

단, 214/216초 화면의 반올림된 거리·신뢰도·중심 좌표를 현재 판단기에 직접 넣으면 둘 다 GO가 나온다.
따라서 그 순간 실제 GO 발행을 막은 단 하나의 조건(모션 잠금, 입력 시각, 당시 실행 코드 차이 등)은
동일 시각의 원본 motion status / motion command / decision debug / hurdle info 없이는 확정할 수 없다.
화면 값 전체가 하나의 동기화된 판단 입력도 아니다. `Go now`와 `Parallel`은 허들 분석기에서,
`Center angle`과 `Stage`는 모션 명령에서, `Phase`는 decision debug에서 가져온다.
실제로 GO가 발행된 224초에도 화면의 `Go now`는 NO다. 이를 실제 GO 진입 여부로 해석하면 안 된다.

추가 조사에서 제어 동작은 변경하지 않았다. 근거리에서 길게 남은 전진 때문에 시야를 잃는 문제를
줄이려면 접근 전진 길이를 점검하고, 근거리 유효 관측을 GO 예약에 활용할 경우에는 관측 나이,
이동량, 정렬 조건을 함께 검증해야 한다. 미검출만으로 허들 넘기를 강행하는 수정은 근거가 부족하다.

## 추가 확인: 공 소실 시 전진/후진 분기

픽업 초기/미세 정렬의 `_pickup_ball_loss_alignment()`는 다음 순서로 판단한다.

1. 마지막 검출 상자가 화면 내부이고 공 소실이 확인됨: 전진 4회 모션을 한 번 요청.
2. 위 전진이 선택되지 않았고 마지막 유효 공의 하단 거리가 100px 이하: 후진 1회 요청.
