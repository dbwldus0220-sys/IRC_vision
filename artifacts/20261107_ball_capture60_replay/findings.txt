60% 수집 / 70% 확정 변경 전후 재현 비교

이번 실행에서 제어 코드/모션/파라미터 추가 변경 없음. ROS 그래프나 실제 모터를 시작하지 않았다.

방법
기존 artifacts/20261107_ball_entry_replay/replay.py의 동일 run()을 사용했다.
변경 전 스냅샷에서 두 변경 메서드를 추출해 before_methods.py에 저장했다.
before 실행에만 메모리에서 메서드를 대체하고, after는 현재 소스 그대로 실행했다.
이는 작업 중인 소스 파일을 되돌리는 방식이 아니다.
기존 10개 조건의 before 결과가 이전 results.json과 일치하는지 assertion으로 확인했다.
추가 조기 관측 조건 4개를 포함해 14개 조건 x 전후 2회 = 28회 비교했다.

주의
원본 프레임별 검출 기록이 없으므로, 이 입력은 영상 전체의 정확한 재생이 아니다.
로그의 첫 후보 시각/12회 확정 시각과 국소 처리량 10.305 FPS, 영상 나이 289.902ms에 맞춘 합성 입력이다.
중간 검출 상자/거리/방향은 일정한 유효 입력으로 가정했다. 실제 영상에 있었던 후보 횟수 감소를 복원하지 않았다.
결과 시간은 현재 모션 완료를 0ms로 한 명령 발행 시각이며 실제 발 움직임 시각이 아니다.
확정 10회와 12회 비교는 기존 변경의 효과이고, 이번 60/70% 변경의 효과와 구분해야 한다.

주요 결과: 변경 전 -> 변경 후 (ms)
기존 기본 조건 12회: +328.338 -> +328.338, 둘 다 사전 예약 없음.
기존 기본 조건 10회: +134.257 -> +134.257, 둘 다 사전 예약 없음.
10번째 관측 누락/10회: +231.297 -> +231.297, 둘 다 사전 예약 없음.
후보 입력 150ms/300ms 앞당김, 10회: 둘 다 경계 0ms에 명령, 사전 예약 없음.
후보 입력 500ms 앞당김, 10회: -171.662 -> -171.662, 둘 다 사전 예약 성공.
영상 나이 600ms: 전후 모두 유효 명령 없음.
추가 후보 입력 800ms 앞당김, 10회: -374.622 -> -471.662 (약 97ms 빨라짐).
추가 후보 입력 900ms 앞당김, 10회: -377.582 -> -571.662 (약 194ms 빨라짐).
추가 후보 입력 1000ms 앞당김, 10회: -380.541 -> -574.622 (약 194ms 빨라짐).
위 조기 조건은 변경 전에도 사전 예약에 성공했다.
14개 비교 조건에서 '사전 예약 실패 -> 성공'으로 바뀐 경우는 없었다.
모든 전후 쌍에서 확정 시각/선택 모션은 같고, 변경 후 명령이 더 늦어진 경우는 없었다.

해석
이번 변경은 60~70% 사이의 유효 관측을 활용해 예약 여유를 늘린다.
그러나 확정 전에 후보를 예약용 관측으로 인정하는 변경은 하지 않았고,
확정 시점 자체나 확정 후 필요한 관측 수(3개)도 바꾸지 않았다.
기존 기본 조건은 공 확정이 모션 종료보다 늦어 60% 수집의 효과가 없다.
따라서 이번 변경만으로 11/7의 실제 멈춤이 해결됐다고 보고하면 안 된다.

추가 확인
test_ball_entry_capture_window.py: 10개 통과, 출력은 window_test_results.txt.
기존 메모리 실행기 재현 실행: 예약 유무 x 시작 준비 가정 0/20/100ms의 6개 조건 모두 통과.
예약한 경우 모션 경계 활성화 지연 0ms/준비 호출 1회,
예약 없는 경우 가정한 준비 지연만큼 지연/준비 호출 2회.
이것은 실제 모터 통신 시간 실측도, 모션 내부 홀드 제거도 아니다.
