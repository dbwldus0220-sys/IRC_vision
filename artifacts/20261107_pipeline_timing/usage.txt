비전 -> 공 판단 지연 기록 (진단 전용)

다음 비전/주행 프로세스 재실행부터 자동 기록한다. 별도 주행이나 모터 동작을 추가하지 않는다.
ROS 콘솔과 기존 ~/.ros/log 실행 로그에 아래 두 태그가 남는다.

[DETECTOR_PIPELINE_TIMING]
- capture_to_detector: RGB 촬영 -> 검출 이미지 콜백 진입 (ROS 시각)
- convert_preprocess: 영상 변환/전처리
- inference: 추론
- postprocess: 기존 추론 시간 집계 호출과 후처리
- publish: 검출 메시지 준비/발행
- overlay_display: 검출 발행 이후 오버레이/표시/주석 이미지 발행 작업
- callback: 검출 콜백 전체 작업 시간 (이번 진단 요약 로그 출력 자체는 제외)
- skipped_total: 기존 processing/max_fps 조건으로 건너뛴 콜백 누적 수

[BALL_PIPELINE_TIMING]
- capture_to_detector: 촬영 -> 검출 콜백 진입
- detector_work: 검출 콜백 진입 -> 검출 메시지 직렬화 직전
- detector_to_ball: 검출 메시지 직렬화 직전 -> 공 분석 콜백 진입
- ball_work: 공 분석 콜백 진입 -> 공 분석 메시지 직렬화 직전
- ball_to_decision: 공 분석 메시지 직렬화 직전 -> 판단 콜백 진입
- capture_to_decision: 촬영 -> 판단 콜백 진입 (ROS 시각)
- decision_callback: 판단 콜백 진입 -> 처리 종료 (진단 로그 출력 이전)

전달 구간에는 JSON 직렬화/발행/ROS 전달/콜백 대기가 포함된다. 네트워크 시간만을 뜻하지 않는다.
화면 작업은 검출 결과 발행 뒤이므로 현재 프레임의 detector_work에 포함되지 않는다.
대신 같은 검출 실행 흐름에서 다음 프레임 처리를 늦출 수 있어 별도 집계한다.

형식
rgb_stamp_ns로 원본 촬영 프레임을 식별한다.
latest_ms는 그 로그에 선택된 한 프레임의 단계별 값이다.
summary_ms는 집계 구간의 각 단계별 유효 샘플 수(n), 평균(avg), 최댓값(max)이다.
기본 집계 주기는 2초이며 프레임 이력을 저장하지 않아 메모리가 늘지 않는다.
새 track_id에서 공이 처음 확정되는 콜백은 confirmation_event=true로 즉시 기록한다.
input_status에는 accepted, capture_time_rejected 등 기존 입력 처리 상태가 남는다.
이후 확정 상태의 모든 프레임을 별도로 출력하지는 않는다.
RGB/분석 메시지에는 diagnostic_timing 메타데이터만 덧붙인다.

시계와 해석
ROS 촬영 시각과 monotonic 시각을 서로 빼지 않는다.
프로세스 간 monotonic 구간은 현재처럼 같은 로봇/호스트에서 실행할 때 비교한다.
서로 다른 호스트의 monotonic 값을 비교해서는 안 된다.
시각이 없거나 음수 구간이면 null로 표시하며 지연 0으로 간주하지 않는다.
화면의 FPS/표시 지연과 실제 입력 전달 지연을 구분해서 읽어야 한다.

변경하지 않은 항목
공 확정 횟수/누적 정책, 예약 수집 및 확정 시점, 관측 유효성 기준, 모션, 토크,
카메라 설정, max_fps, 화면 갱신 빈도, QoS와 실행기 스케줄링을 변경하지 않았다.
추가된 시각 읽기/메타데이터 직렬화/로그 출력에는 소량의 실행 비용이 있다.
진단 로그는 제어 판단 이후에 출력하고, 진단 실패가 제어 처리를 중단하지 않게 했다.

검증
관련 테스트 결과는 test_results.txt.
진단 메타데이터 유무/불일치/손상 조건에서 발행 제어 명령 및 예약 ID가 동일함을 확인했다.
기존 로그 기반 합성 재현 10개 전후 결과(명령 시각, 예약 여부, 확정 trace)가 완전히 같았다.
실제 모터/카메라 테스트는 실행하지 않았다. 다음 평소 테스트 기록으로 병목을 확인해야 한다.
