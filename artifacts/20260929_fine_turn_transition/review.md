# 미세 전진 후 제자리 회전 준비 및 BALL 카메라 하향

## 적용 범위와 순서

모든 미션이 사용하는 `motion_command_bridge_node.py`의 공통 전송 경로에서 다음 순서를 적용했다.

1. 실제 미세 전진의 성공 완료를 기록한다.
2. 다음 동작이 제자리 좌/우회전이면 준비 자세를 먼저 요청한다.
3. 준비 자세의 SUCCEEDED를 받은 뒤 원래 회전을 요청한다.
4. 회전이 끝날 때까지 원래 command_id/request_id와 모션 잠금을 유지한다.

미세 전진 대상은 `ball_general_fine_forward_8`, `pickup_fine_forward_0`, `goal_camera_90_fine_forward_1..4`다. 이 별칭은 BALL뿐 아니라 허들 근거리 처리에도 사용된다. 라인/공/허들/골대/픽업 정렬에서 공통 경로를 적용한다. 이동하면서 방향을 보정하는 line_recovery 계열은 제자리 회전과 구분하여 불필요한 준비 자세를 넣지 않는다.

제자리 회전을 미리 예약한 경우에도 진행 중인 미세 전진의 완료까지 브리지에서 기다린 뒤 준비 자세를 선택한다. 실패/취소된 미세 전진 뒤에는 예약 회전을 실행하지 않는다. 준비 자세 실패·취소·거절·시간 초과는 `TURN_PREPARATION_FAILED`로 전달하며 원래 회전은 실행하지 않는다. 픽업의 기존 복구 가능한 모터 오류 정책도 준비 자세 실패를 건너뛰지 못한다. 준비 자세의 중복 완료 메시지는 실제 회전을 완료시키지 않는다.

직전 미세 전진과 회전 사이에 다른 실제 동작이 완료됐다면 오래된 미세 자세 이력으로 준비 모션을 추가하지 않는다. 연속 회전에도 준비 모션을 반복하지 않는다.

## 카메라 각도 선택

- 45도: `fine_to_turn_ready_45` → `찐미세오뒤에서 오뒤(45도)`.
- 0도: `fine_to_turn_ready_0` → `찐미세오뒤에서 오뒤(0도)`.
- 골대 90도: `fine_to_turn_ready_90` → `찐미세오뒤에서 오뒤(골대 카메라90도)`.

공/허들의 하향 유지가 활성화되어 있으면 최근 실행기 heartbeat를 반영하여 0도 준비 자세를 선택한다. 픽업 0도 회전 또는 직전 미세0도 전진도 0도를 선택한다. 골대90도 회전은 90도 준비 자세를 선택한다.

제공 파일에는 회전 준비 90도 모션이 없어, 기존 골대 시야를 유지하는 선택을 사용자에게 질문했다. 추가 답변이 없는 상태에서 기존 카메라90도 유지로 진행한다고 알리고, 45도 모션의 몸 프레임을 그대로 사용하여 모터0 값만 기존 골대값 1.0도로 맞춘 파생 모션을 만들었다. 이는 카메라90도에 대응하는 서보 각도이며 서보에 90.0도를 명령한다는 뜻이 아니다.

파생 모션의 자세 이름에는 `(회전준비90도)`를 붙였다. 기존 시작 자세 `오뒤412`와 이름이 같으면서 카메라 각도가 달라지면 시작 자세 검색이 모호해지므로 이를 방지한다. 원본 45도/0도 모션의 프레임, 각도, 토크, 시간, 반복 횟수는 유지했다.

## BALL 하향 동작

기존 검출 및 화면 하단 요청 조건(`detected == true`, `head_down_requested == true`)은 유지했다. 분석기의 하단 기준은 120 px이며, 550 mm 픽업 진입 조건과는 별개다.

- `line_recovery_left_4`, `line_recovery_left_6`, `line_recovery_right_4`를 하향 허용 목록에 추가했다.
- BALL 미션이 제어하는 접근/정렬 중에는 특정 전진 모션이 실행 중인지에 관계없이 하향 요청을 적용한다. 정지/새 영상 대기와 제자리 회전 중에도 적용된다.
- BALL 미세 전진과 pickup 접근 전진 별칭도 허용 목록에 추가했다.
- 하향 후 `ball_camera_down_forward_2/4`가 시작되더라도 하향 유지를 해제하지 않는다.
- 기존의 400 ms 보간으로 모터0을 -64.0도(이 프로젝트의 카메라0도 자세)로 덮어쓴다.
- 거절된 cancel/잡기 요청은 카메라 유지를 해제하지 않는다. 실제 CANCELLED 또는 실제 잡기 동작 RUNNING이 확인되어야 해제한다.
- 실제 `pickup`/`sdk_pickup`의 잡기 동작부터는 원래 카메라 프레임을 유지한다. 잡기/잡기 확인 모션에는 접근0도와 다른 카메라 값이 들어 있으므로 재검출로 접근용 하향이 재활성화되지 않도록 했다. 다음 BALL 미션에서는 다시 하향 가능하다.
- GOAL/HURDLE이 이미 소유한 카메라 유지 보호는 보존했다.

## 카탈로그와 허용 오차

입력: `/home/jet/Downloads/robot_motions(33).json`.

`source_robot_motions33.json`은 입력 파일을 그대로 보관한 사본이다. 요청에 필요한 두 원본 모션과 90도 파생 모션만 추가했으며 기존 86개 모션의 내용은 바꾸지 않았다. 실행 카탈로그는 총 89개이고 모두 `completion.position_tolerance_deg = 5.0`이다. 별칭도 이 세 항목만 추가했다. 변경 전 실행 카탈로그와 별칭은 `runtime_before.json`, `aliases_before.yaml`에 보관했다.

실행 인수 `position_tolerance_enabled`의 기본값은 true다. 사용자가 실행 시 false를 지정하면 값이 5도여도 완료 위치 검사는 생략되므로, 5도 검사를 사용할 때는 true로 실행해야 한다.

## 검증 결과와 적용

- C++ `sdk_motion_executor` 빌드 성공.
- 브리지, 새 미세 전진/회전 테스트, 카탈로그 계약: **506 passed, 17 failed**.
- 실패한 카탈로그 계약 17건은 변경 전 카탈로그/별칭/테스트로 동일하게 재현했다. 신규 실패는 없다.
- 신규 검증에는 각 미션의 좌/우회전, 카메라0/45/90 선택, 준비 실패/취소/거절, 예약 회전, 중복 상태, 다른 동작 후 과거 자세 이력 제거, 원본 프레임 보존, 시작 자세 이름의 유일성, 전체 5도 허용 오차가 포함된다.
- 격리된 ROS_DOMAIN_ID=176과 별도 토픽에서 simulated backend로 BALL/GOAL/HURDLE 카메라 launch 테스트 **3/3 통과**. 하드웨어는 활성화하지 않았다.
- 모션 검증 도구: 89개 모션, 모든 별칭 연결 및 관절 ID 0..22 검사 통과.
- `git diff --check` 통과.

기존 install은 빌드 실행기 및 소스에 연결되어 있으므로 실행 중인 프로세스를 재시작하면 새 코드가 반영된다. 실기 동작은 실행하지 않았다. 모의 테스트는 명령 순서/성공 조건/카메라 유지 상태를 확인하며 실제 균형을 검증하지 않는다. 실기 적용 전 시뮬레이션에서 자세 전환 시 지지 상태, 정지/회전 연결, 하향 중 바닥 투영 조향값과 공 검출 유지 여부를 확인해야 한다.
